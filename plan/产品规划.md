# 口语练习网站 - 产品规划

> 本文档定义项目的核心需求、功能规划、技术选型和实施路线，后续所有设计和实现均以此为依据。

---

## 一、项目背景

### 1.1 项目定位
一个帮助用户练习英语口语的 Web 应用，通过 AI 技术提供低成本、高质量的互动式学习体验。

### 1.2 目标用户
- 英语初学者：需要基础对话练习和发音纠正
- 进阶学习者：需要真实场景对话和表达优化
- 备考人群：雅思/托福口语练习

### 1.3 核心价值主张
- **低成本运行**：AI 对话接入高性价比模型，发音评分采用开源方案
- **真实对话体验**：对话自然流畅，像与真人交流
- **综合提升**：不仅练口语，同时提升表达方式和词汇量

## 二、运行环境

### 2.1 硬件配置
| 项目 | 配置 |
|------|------|

| 内存 | 4 GB |
| 硬盘 | 50 GB SSD |
| 操作系统 | Linux (Ubuntu 20.04 LTS 或更高版本) |

### 2.2 数据库选型
- 采用轻量级嵌入式数据库（如 SQLite），无需安装额外数据库服务
- 适合小型到中型应用的并发量
- 零外部依赖，部署简单

- 所有第三方开源项目统一存放在 `third-party/` 目录下
- 便于管理语音评测等本地部署的开源组件
- 方便后续固定产品状态和版本控制

### 2.4 发音评测选型约束
- **必须使用开源方案**，不使用第三方收费 API
- 根据 2 核 4G 硬件要求进行严格选型，避免选择对性能要求过高、无法在低配服务器运行的项目
- 优先选择在 CPU 推理环境下表现良好的轻量级方案

## 三、核心功能模块

### 3.1 AI 口语对话（P0 - 核心功能）✅ 已确定

#### 3.1.1 AI 模型选型
- 接入高性价比 LLM API，追求低成本高自然度
- 推荐候选：Qwen-Turbo（阿里云）、GLM-4-Flash（智谱）、Moonshot-v1（月之暗面）
- 对话需像人类自然对话，非机械式回复

#### 3.1.2 兴趣气泡引导
- **页面打开时展示兴趣气泡**：用户可以选择感兴趣的话题开始对话
- **随机按钮**：点击后随机分配一个对话主题
- **自由开始**：用户也可以不选气泡，直接输入任意内容开始对话

#### 3.1.3 对话模式
- **自由对话模式**：与 AI 进行自然英语对话
- **场景对话模式**：模拟特定场景（餐厅点餐、面试、旅行等）
- **话题推荐**：基于热门兴趣标签智能推荐

#### 3.1.4 实时辅助
- **语法纠错**：对话过程中即时指出语法/用词错误
- **表达建议**：当有更地道的表达方式时，给出优化建议
- **词汇拓展**：推荐更精准或高级的同义词替换

#### 3.1.5 输入方式（2026-10-17 新增）
- **键盘输入（保留）**：现有 textarea + Send，始终可用，不受语音功能影响
- **按住说话（微信式）**：按住录音按钮开始录音 → **松开即发送并开始对话** → **向上滑动则取消**（丢弃本次录音，不发送）
  - 需给出时长与取消阈值提示；滑动距离阈值约 60–80px；松手前上滑即弃，避免误发
  - ⚠️ **长按不得触发浏览器自己的手势**（2026-10-24 真机反馈：长按会弹出"复制"菜单）。三层都要堵：
    ① **`-webkit-touch-callout: none`** —— iOS 的长按菜单只认这个属性，`user-select: none` 管不住它，而 **Tailwind 3.4 没有对应工具类**（`select-none` 构建产物只有 `-webkit-user-select/-moz-user-select/user-select`，实测全量 CSS 里 `touch-callout` 出现 0 次），故自建 `.no-callout` 于 `global.css`；
    ② `pointerdown` 里 `preventDefault()`，抢在浏览器把这次手势判成"长按选词"之前声明占用；
    ③ `contextmenu` 与 `dragstart` 阻止默认（Android 长按走的是上下文菜单）
  - ⚠️ **`pointercancel` 必须归还麦克风**：浏览器一旦接管手势就发 `pointercancel`，**之后不会有 `pointerup`**。原实现只把它当作"上滑取消"设了个标志位，结果 `MediaRecorder` 继续录、麦克风指示灯常亮，而 `pointerDown` 又以 `recorder.recording` 提前返回 → **按钮卡死到刷新为止**。现在松开与手势被夺走共用一个幂等收尾 `finish()`；且手势被夺走**不是用户主动取消**，所以按"发送"处理，避免用户的录音静默丢失
- ⚠️ **实现路线必须由服务端 STT 承担，不能沿用浏览器 Web Speech API**：
  - `SpeechRecognition` 自带独立音频管线、会自行断句停顿，**无法可靠地按"按住/松开/上滑取消"控制**，也不返回音频
  - 而 `MediaRecorder`（已落地的 `useRecorder`）产出的 webm/opus 正好交给**已跑通的 faster-whisper 服务端 STT** 转写 —— 一份音频同时用于「转写成消息」和「发音/内容评分」
  - 附带收益：Safari / Firefox 也能用语音输入（满足 4.2 兼容性；Web Speech API 实际仅 Chrome 系可用）
  - 代价：识别延迟从浏览器本地变为一次服务端推理（开发机实测 3.17s 音频 → 2.28s 推理，**RTF 0.72 为 4 核所得，2 核 4G 需重测**）；且录音必须上传，需在隐私说明中写明

#### 3.1.6 局域网真机验证的前置条件（2026-10-24 新增，开发环境）

「按住说话」要在手机上验证，必须**同时**满足两件互相独立的事，缺一个都不通。

**① 手机要能路由到 dev server —— 当前不满足**

| 取证项 | 实测值 | 结论 |
|---|---|---|
| WSL `eth0` | `172.23.101.216/20`，MAC `00:15:5d:59:71:c4` | `00:15:5d` 是**微软 OUI** → Hyper-V/WSL 虚拟网卡 |

> ⛔ **mirrored 路线已排除**（原推荐作废）：官方文档原文 —— *“On machines running **Windows 11 22H2 and higher** you can set `networkingMode=mirrored`”*（`learn.microsoft.com/windows/wsl/networking`，已抓取 http=200）。本机是 **Windows 10 19045**，WSL 版本再新也不满足 OS 要求。
> 同页还表明 `dnsTunneling`、`autoProxy`、**Hyper-V 防火墙默认开启**同样限定 Win11 22H2+ → 之前记的「mirrored 下 Hyper-V 防火墙是否拦入站」**在 Win10 上是伪问题**，要处理的只有普通 Windows Defender 防火墙入站规则。
>
> 结论：`172.23.101.216` 只有 Windows 宿主机自己可达，**同 WiFi 的手机不可达**；此前"改用 `http://localhost:5173` 解决麦克风"只对**本机浏览器**成立，对手机无效。

**② 安全上下文 —— 手机只能靠 HTTPS**

`localhost` 是 http 唯一的豁免地址，所以本机走 `http://localhost:5173` 就能录音；手机没有这个豁免，必须是 `https://<手机地址栏里那个地址>`。

已离线验证（openssl 3.5.5 + node TLS）：

- 自签证书必须把访问地址写进 **SAN**（只写 CN 无效）：按 IP 访问 `authorized=true`；用不在 SAN 里的地址校验 → `ERR_TLS_CERT_ALTNAME_INVALID`，证明 SAN 真的生效
- 本地根 CA 签发后 `openssl verify -CAfile rootCA.crt dev.crt` → OK；**不导入该 CA 时一律 `UNABLE_TO_VERIFY_LEAF_SIGNATURE`，就是浏览器那张警告页**
- Vite 5 的 `server.https` 直接接受 `{ key, cert, ca }`（`vite/dist/node/index.d.ts:389-393`）→ **不需要 `@vitejs/plugin-basic-ssl`**，这台机器少一个依赖就少一次 npm 网络风险
- 前端 `baseURL: '/api'` 是相对路径，由 vite 服务端代理到 `http://localhost:8000` → **切 https 不产生混合内容、也不必改 `CORS_ORIGINS`**（浏览器看到的始终同源）；录音回放的 blob 同理
- ⚠️ **`https` 与「不再提示不安全」是两件事**：只要拿到安全上下文，麦克风就能用，点掉警告页即可；想让地址栏变锁，必须把根 CA 装进**手机**的信任库

**已落地（2026-10-24，全部离线验证）**

- `src/frontend/scripts/dev-cert.sh`：自建根 CA + 带 **IP SAN** 的叶子证书（openssl，零新增依赖）。幂等 —— 同参数复用；**`--ip` 变了自动重签**（Windows 是 DHCP，地址变了旧证书就会 `ERR_CERT_COMMON_NAME_INVALID`）；根 CA 不变，手机只需装一次
- 产物在 `src/frontend/.certs/`，**已进 `.gitignore`**（私钥 600，绝不入库）
- `vite.config.ts`：`DEV_HTTPS=1` 才开 https，**默认仍是 http**（不打断本机 `localhost` 开发流）；证书缺失时**显式报错并给出修复命令，不静默退回 http**
- `npm run dev:https` / `npm run cert`
- 验证（在 WSL 内用 `curl --resolve 192.168.5.84:5197:127.0.0.1` 冒充手机地址）：① 带 rootCA → `http=200` ② https 页面里同源 `/api/health` 正常返回（无混合内容、CORS 未动）③ 不在 SAN 里的地址被拒 ④ 不信任 rootCA 被拒 ⑤ 缺证书启动即报错。**这些只证明 TLS 层正确，不等于手机链路已通**

**三条可行路线（2026-10-24 更新：当前采用第 ③ 条）**

| 路线 | 手机访问地址 | 安全上下文从哪来 | 状态 |
|---|---|---|---|
| ① portproxy + 本机自签 https | `https://192.168.5.84:5173` | vite 自己出证书 | 证书/脚本已就绪，未走通（需管理员 PowerShell） |
| ② mirrored 网络 | 同 ① | 同上 | ⛔ **Win10 不可用**（需 Win11 22H2+） |
| ③ **花生壳内网穿透** | `https://<随机>.vicp.fun` | **花生壳边缘终结 TLS**，vite 在幕后继续跑 http → **不需要本机证书** | ✅ 已打通到 vite（手机收到过 vite 的响应页） |

③ 的必做项与已验证事实：

- `vite.config.ts` 加 `server.allowedHosts: ['.vicp.fun']`。Vite 5.4.21 按 **Host 头**做 DNS-rebinding 校验，源码里 `net.isIP(hostname) === 4` 与 `localhost` **隐式放行** —— 这解释了为什么局域网 IP 从不触发、换成语名域就被拦
- 前导点 = 该域及其任意子域（实现：`allowedHost[0] === '.' && hostname.endsWith(allowedHost)`），故**不必**跟着花生壳的随机子域反复改
- 实测（WSL 内用 `--resolve` 造 Host 头，未依赖隧道）：`*.vicp.fun → 200`、`evil.example.com → 403`（防护未被整体关闭）、`localhost → 200`
- ⚠️ **改 vite 配置需要重启 dev server 才生效**（用户自己的实例已自动热重载验证过）
- ⚠️ **助手侧无法端到端验证隧道**：这台 WSL 出网受限，`curl https://<隧道域>` 直接 `http=000` —— **这是本地出网限制，不是隧道故障**，判定必须以手机实测为准
- ⚠️ 未验证：HMR 的 websocket 能否穿过花生壳（不能也只是失去热重载，手动刷新即可）；隧道带宽/延迟会叠加到 STT 往返上

**仍需用户提供 / 待实测**

- 手机系统（Android / iOS）；走花生壳时**地址栏必须是 `https://`** —— 若用 `http://` 打开隧道域名，依旧不是安全上下文，麦克风照样被拒
- ⚠️ **暴露公网期间的风险**：`POST /api/auth/register` 实测返回 **201**（注册公开），意味着隧道开着时任何人都能建账号并打后端；`.env` 已覆盖 `ADMIN_PASSWORD` 与 `JWT_SECRET_KEY`（未用默认值），但**测完请关隧道或加访问口令**
- ⚠️ **portproxy 路线的遗留风险（若回退到 ①）**：WSL IP 每次重启会变导致 `connectaddress` 失效；Windows Defender 入站默认策略可能仍拦 5173；路由器开 AP 隔离时手机到 PC 任何端口都不通
- ⚠️ iOS Safari 在证书链不受信时是否仍拒绝 `getUserMedia`（即"点过警告"够不够）—— 未验证，iPhone 走路线 ① 时请老实装根 CA；走路线 ③ 时花生壳用的是它自己的公网证书，正常不受信问题

### 3.2 发音评测（P0 - 核心功能）✅ 已确定

#### 3.2.1 技术选型 ✅ 已定案（2026-10-17）
- **采用开源方案**：不使用第三方收费评测 API；权重存放于 `third-party/`（已 gitignore，不入库）
- **选定：[faster-whisper](https://github.com/SYSTRAN/faster-whisper) `base.en`**（CTranslate2 + int8，CPU 推理），**做词级评测**；同一引擎兼作服务端 STT
- ⚠️ **原推荐候选已被实测推翻**（核查方式：PyPI 元数据 + 内嵌 README 关键词统计）：
  - `ESPnet`、`PaddleSpeech`、`SpeechBrain` **均不提供发音评测（CAP）能力** —— ESPnet README 中 "pronunciation"/"phoneme" 命中 **0**，只给 ASR + 强制对齐构件；音素级 GOP 需自行搭建
  - 三者都要拖 **torch**（cp312 wheel 554.6 MB，装完 GB 级），在 2 核 4G 上风险高；`paddlespeech` 另有 71 个直接依赖
  - `fish-speech` 是 **TTS** 项目、且 **CC-BY-NC-SA**（非商用），本就不能做评测
  - NeMo 等资源消耗大的方案照旧不采用
- **落地要求**：权重目录需四个文件平铺且保持原名 —— `config.json`、`model.bin`、`tokenizer.json`、**`vocabulary.txt`**（缺后者报 `Cannot load the vocabulary from the model directory`）；`config.json` 必须含 `alignment_heads`，否则拿不到词级时间戳。huggingface.co 在本环境不可达，须手工放置（镜像 `hf-mirror.com` 可用但不稳）

#### 3.2.2 评测维度（当前实现为词级，音素级待后续）
- [ ] **音素级别准确度**：未实现 —— 需音素 CTC 模型 + 强制对齐 + 自实现 GOP
- [x] **整体评分**：准确度（1−WER）、流利度（词/秒 ÷ 2.8 目标 + 停顿惩罚）、完整度（未漏读比例）加权成 overall
- [x] **音标对比显示**：显示参考词的**标准音标**（`eng_to_ipa`，离线随包数据）；不显示"实际发音音标"（无音素模型，不做假数据）
- [x] **问题定位**：定位到**词**（matched / substituted / missing，附实际听到的词与时间戳），非音素级
- ⚠️ 单词分数来自 **ASR 识别置信度**，是发音的**代理指标** —— 可能"听对了但发音差"，响应里的 `note` 已明确标注
- 🔧 **对齐已改为忽略大小写**（2026-10-23）：`tokenize` 保留原句大小写用于显示，比较走 `_norm()`（小写 + 去尾撇号）。此前 Whisper 的小写输出对不上参考句的大写词，**每个大写句首词都算"读错"**：合成一条 5 句首字母大写的完美跟读实测 `WER 20% / accuracy 80`（应为 0/100），3 条真实跟读里只有 1 条受影响的幅度较小（对齐 0.61→0.69）
- ➕ 同时对齐结果新增 **`alignment`（参考句中被正确识别的词占比）**，它不是给学习者看的分数，而是 3.2.7 "没照读"闸门的判据
- ⚠️ **库里历史评分行是旧算法产物**（含大小写缺陷与旧容错逻辑），与新记录**不可直接混在一起做趋势对比**；3.2.5 的图表功能上线前需说明这一点，或按 `created_at` 分段

#### 3.2.3 内容评分 ✅ 已实现
- [x] **词汇复杂度评分**、**句式多样性评分**、**表达地道性评分**（当前为文本启发式：词汇总量/去重率/平均词长，Phase 2 计划换 LLM 精评）

#### 3.2.4 两种评测模式（2026-10-17 新增）

| 模式 | 触发方式 | 参考文本来源 | 能评什么 | 不能评什么 |
|---|---|---|---|---|
| **跟读评测**（已实现） | AI 气泡上「🎙️ 跟读评测」 | 该条 AI 消息原文 | 发音准确度(1−WER)、完整度、流利度、逐词 matched/substituted/missing、标准音标 | 音素级（待 GOP） |
| **自由表达评测**（2026-10-22 调整） | 3.1.5 按住说话发出后自动评 | **无**（用户自发内容） | 发音**代理分**（ASR 逐词置信度均值）、流利度（词/秒 + 停顿）、有效语音占比、内容三项、逐词 `unclear` 标记 | ⚠️ **不计算 WER / 漏读 / 错读**（`wer=null`） |

> ⚠️ **为什么自由表达的发音只能是代理分**
> 没有目标句就无法做词级对齐，因此拿不到 WER，也就没有"漏读/错读"。可行的替代是**服务端自己转写这份音频**并取逐词置信度：含糊、吞音、录音过轻都会压低置信度，方向正确。
> 但它是 **ASR 清晰度指标，不是音素准确度** —— 可能出现"发音差但用词常见、被听对了"从而得高分。界面与 `note` 必须显式写"发音代理分"，**禁止呈现为音素级结论**。
> 2026-10-22 用户要求把自由表达也接入发音评测（原方案留空），实现改为服务端转写后打分，内容与发音分**同源**（都基于服务端听到的文本，不采信客户端传来的文本）。

#### 3.2.5 评分展示与持久化（2026-10-17 新增）
- [x] **折叠展示**：评分卡默认收起为一行摘要（模式 + 总分 + WER），点击展开明细；展开后为紧凑排版（三指标一行三栏、`text-xs`、听到的一行截断），且**首行显示原句**，避免评测面板把练习句挤出视野
- [x] **保存评分数据**：已建 `pronunciation_scores` 表，一次评测一行：
  - `mode`(read_aloud/free)、`reference_text`、`heard_text`、三项分数 + 总分、`wer`（free 为 NULL）、逐词结果 JSON、关联 `message_id` / `audio_asset_id`、`pron_engine_available`、`engine`、`created_at`
  - 回读接口：`GET /scores?conversation_id=`（整会话一次取回）与 `GET /scores/{message_id}`；进入对话时自动取最近一条，折叠卡片重进后仍可展开
  - 历史趋势与 3.4「能力评估」的数据基础已具备（图表 UI 仍待做）

#### 3.2.6 评分的呈现位置（2026-10-22 新增，重要）

**要求：评分必须跟着对话走，而不是集中在输入框上方的一块面板里。**

- **每句话自带评分**：学习者每一条语音消息（按住说话发出的那句）下方，**就地显示一个粗略分数**（总分 + 一句结论），随消息一起滚动、一起留在历史里
- **明细就地展开**：点击该分数才在原位展开详情，展开不影响其他消息的位置
- **不再把详情堆在输入框上方**：那里只保留"正在录音 / 识别中 / 错误提示"这类**过程态**信息，评测结果不放这儿
- 跟读评测（针对某条 AI 消息的复述）同理：分数挂在那条被跟读的消息下方，而不是全局面板

> ⚠️ **实现含义（写死在需求里，避免又退回全局面板）**
> 1. 评分是**按消息**存储与渲染的 —— 已有的 `pronunciation_scores.message_id` 正是为此准备；
>    自由表达挂学习者自己的消息，跟读挂被复述的那条 AI 消息
> 2. 因此不能再用"单个 `card` 状态 + 固定面板"的写法；需以 `message_id → 评分` 的映射渲染，
>    数据源用 `GET /scores?conversation_id=`（一次取回整会话，天然覆盖刷新/重进）
> 3. 就地展开要求每条消息各自持有展开状态，不能共享一个全局开合标记

**实现状态（2026-10-22）**：上述三点均已落地 —— `ChatPage` 改为 `message_id → 评分` 映射（不再是单个 `card` + 固定面板），数据源 `GET /scores?conversation_id=`（整会话一次取回，刷新/重进自动恢复），展开状态由各消息自己的 `<details>` 持有；输入框上方只保留"正在录音 / 停止并评分 / 识别中 / 错误"过程态。

- 跟读分挂在**被复述的那条 AI 消息**下方；按住说话分挂在**学习者自己的消息**下方
- 每条消息只显示最新一次评测（后端按 `conversation_id` 返回、前端取每个 message 的首条即最新）

> ⚠️ **一个未闭合的语义缺口（需产品决定）**
> "每一句话都跟着评分"目前只对**语音消息**成立：打字发出的消息没有音频，无法评发音。
> 但内容分（词汇/句式/地道性）本来就只吃文本、且是本地启发式零成本，技术上可以给每条打字消息也挂一个内容分。
> 是否这样做会改变界面语义（分数不再是"发音分"而是"表达分"），需确认后再接，不擅自扩范围。

#### 3.2.7 评分前的「这次没法评」闸门（2026-10-23 新增，修掉两个真机缺陷）

两条都是真人录音暴露出来的（见 Phase 2.5），根因相同：**词级指标把"没说这句话"和"说得不好"混成一件事**。

| 场景 | 实测样本 | 旧行为（错） | 现行为 |
|---|---|---|---|
| **静音/过短** | 12.06s 录音里只有 `'Hello?'`（语音跨度 0.7s，占 6%） | 照样评分，给出一个看起来很低的总分， learner 以为是发音差 | **拒绝评分**，`reject_code=silent`，提示"没听到有效语音…请完整录下你要练的那句" |
| **没照读** | 8.76s 说的是另一句完全不同的话（对齐 0.00–0.43） | 旧算法判 `overall=35.2` / 库里现存 58.5、49.7 这类假分数 | **拒绝评分**，`reject_code=not_read_aloud`，并**回显服务端听到的内容**让学习者自己对照 |

阈值由**磁盘上 10 条真实录音实测标定**，不是拍脑袋：

- `MIN_SPEECH_MS = 800`：静音条 0.7s，最短的真实条 1.7s（`'Hello?'` 在 2.8s 里，60%）—— 分得开
- `MIN_SPEECH_RATIO = 0.15` 且 `MIN_LONG_TAKE_MS = 4000`：只在足够长的录音上判"大部分是静音"，避免误杀短答
- `MIN_READ_ALIGNMENT = 0.5`：真实跟读落在 **0.52 / 0.61 / 0.69 / 1.00**，没照读落在 **0.00 / 0.43 / 0.46**，边界取中间

**硬性约束（写死在实现里）**
- `available` 描述**引擎**，`attempt_ok` 描述**这一次录音** —— 二者不可合并：引擎正常但录音没法评，是 `available=true, attempt_ok=false`
- **被拒的录音一律不写 `pronunciation_scores` 行**，否则"趋势/能力评估"会被 0 分污染（3.2.5、3.4 的数据基础就废了）
- 但**录音本身照旧保留**（`audio_assets` 行 + 文件）：让学习者回听自己到底说了什么，正是这条拒绝最有价值的反馈
- UI **禁止把 `overall=0` 直接显示成"0 分"**：收起态显示"未听清 / 未跟读"字样（`ChatBubble`），展开态显示原因 + 原句 + 听到 + 回听入口
- 判定放在 `pronunciation_service.assess_attempt()`，**跟读与自由表达共用同一实现**，只在 `m is not None`（有参考句）时才走对齐闸门

> ✅ 端到端实测（本地模型，零调用费用）：静音条与"没照读"条均被拒且**未新增评分行**；真实跟读条通过并落库一行，21 词里 18 词带时间戳（可逐词回听）。

#### 3.2.8 原声回放（2026-10-23 新增）

需求：学习者要能**听自己的录音**，比看数字更容易定位发音缺点。

- **整段回放**：评分卡内 `▶ 我的原声`
- **逐词回听**（本功能的价值所在）：词级时间戳早已存在 `words_json`，点击问题词 chip 即从该词 `start` 播到 `end + 0.15s` —— 把"哪个词不对"从推测变成可听
- 历史评分同样可回放：`ScoreRecordOut.audio_asset_id` 已在返回体内，刷新/重进后仍可用
- 一次只允许一条在播（`useRecordingPlayer` 模块级互斥），否则多条消息的卡片会互相盖
- **必须走 blob**：`fetchRecordingUrl()` 用 axios 带 `Authorization` 取二进制再 `URL.createObjectURL` —— `<audio src>` 不会带 JWT 头，直连受保护路由只会 401

⚠️ **顺带修掉一个隐私缺陷**：`main.py` 原先把整个 uploads 目录以 `StaticFiles` 挂在 `/uploads`，**而用户录音与 TTS 输出同目录**，等于所有学习者录音在没有鉴权的 URL 上可读（`/uploads/audio/user-<uid>-<mid>-*.webm`，文件名含用户/消息 id）。回放功能一旦建在这条挂载上就是公开人声，故：

- 移除静态挂载（`nginx.conf` 与 `vite.config.ts` 的 `/uploads` 转发同步删除，否则留下指向已不存在路由的死配置）
- 学习者录音 → `GET /api/pronunciation/recordings/{asset_id}`，**仅本人可读**：他人一律 **404**（沿用本项目"不暴露资源是否存在"的语义，不是 403），文件已被保留策略清走 → **410**（诚实区分"没有"和"已过期"）
- AI 合成音 → `GET /api/speech/tts-file/{name}`，文件名用 `^tts-[0-9a-f]{32}\.mp3$` 严格校验后放行：内容是模型已写出的回复、不是学习者人声，且 uuid 名不可猜；`useSpeak` 里 `new Audio(url)` 无鉴权头也能继续工作
- 旧数据不迁移：历史 `tts-*.mp3` 仍在磁盘、只是不再可从公开路径读取

**两条已知限制（不是缺陷，但必须知道）**
1. **被拒的尝试刷新后会消失**：它不写 `pronunciation_scores` 行，所以重进对话时没有卡片、也就没有回听入口（当前会话内仍在）。
   若以后要让"未跟读"也留痕，需给评分表加状态列并迁移，**不能**为了留痕而写 0 分行——那等于把 3.2.7 又推回去
2. **被拒录音仍占用磁盘直到对话被删**：它写了 `audio_assets` 行，所以 30 天的 `purge_orphan_audio`（只清"无库行引用"的文件）不会碰它；
   真正回收发生在该对话进回收站满 7 天（或被强制删除）时。存储上限若要吃紧，需另加"按天清理无评分录音"的策略

#### 3.2.9 听见 AI 回复：朗读链路与自动播放（2026-10-24 新增）

**手机端 🔊 Listen 没声音的根因**（取证所得，非猜测）：`ChatPage` 调的是 `speak(text)`，**第二个参数 `audioUrl` 从来没传过**，而 `ChatReply.tts_url` 在前端只出现在类型定义里、**无任何消费者** —— 所以朗读一直 100% 走浏览器 `speechSynthesis`。手机缺英文语音包时 `speak()` **不报错、纯静默**，而 `onerror` 又只把状态置回 false，于是表现为"点了没反应"。桌面能响是因为 Windows 自带英文语音，长期掩盖了这个缺陷。

**朗读优先级（`useSpeak` 已按此重写）**

1. **服务端 edge-tts mp3 优先**：`POST /api/speech/tts` → `/api/speech/tts-file/{name}`（免鉴权 + `^tts-[0-9a-f]{32}\.mp3$` 严格校验，见 3.2.8 / 4.3），`<audio>` 可直接播，**手机不依赖任何本地语音包**，且发音是稳定美式英语 —— 口语练习本来就该优先
2. 服务端不可用（`audio_url: null` 或播放失败）→ 回落浏览器 `speechSynthesis`
3. 两条都不通 → **必须显示提示**

> ⚠️ **硬性约束：任何失败路径都不得只留沉默。** 本项目已两次因"静默失败"被误读为服务没起来（edge-tts 403 时返回 `None`、非安全上下文时麦克风报 `not-allowed`），UI 必须给出可读原因。

**自动播放**（用户要求"对话生成后直接播放出来，像是在对话"）：标题栏 `🔊/🔇 自动播放` 开关，选择存 `localStorage`

- **打开旧对话不得朗读历史**：`messages` 首次到达只做"播种"，之后只播新增的尾部消息
- **幂等**：按 `message_id` 记账 —— `send()` 结束后 store 会整体替换消息数组，effect 重跑不能重复朗读
- **录音前必须先打断播放**：`ChatInput` 新增 `onRecordStart`，在**按下手势内**停掉正在播的回复；否则扬声器会把 AI 的声音录进麦克风，再被当作学习者的发音评分
- ⚠️ **iOS 只在真实触摸里允许起播**：在输入区 `onPointerDown` 用 10ms 静音 WAV 预热音频元素（`utils/silentWav.ts` **按字节构造** —— 先前手粘 base64 被换行截成 116/124 字节，解锁静默失效）；被 `NotAllowedError` 拦下时给可操作提示，不沉默
- 成本提示：自动播放＝**每条回复一次对 Microsoft 端点的出站请求**（免费但受网络影响，历史 403 见 Phase 1），并在 `uploads/audio` 落一个 mp3，30 天后由 `purge_orphan_audio` 回收

**验证状态**：`tsc` / `eslint` / `build` 全绿，后端 `pytest` 38 项通过（含 `TestTTSUrlContract`，`_edge_tts` 打桩，**未实际调用 Microsoft 端点**）；`MAX_SERVER_TTS=2000` 与后端 `max_length=2000` 已核对一致。
⚠️ **真机状态：当前验证平台是 Android**（Chrome + 花生壳隧道），修复后的实际出声与自动播放**待反馈**；**iOS 完全未测** —— 那套静音 WAV 起播解锁主要是为 iOS 准备的，Android 上是否必要未知。反馈明细见 `plan/用户反馈.md`。

#### 3.2.10 界面双语（2026-10-25 新增，对应建议 1「纯英文不好理解」）

**用户定的边界**：多语言**只覆盖界面显示**，对话框内容维持现状 —— AI 回复、逐词反馈里的 `expected_ipa`、后端 `detail` 报错串都**不翻译**。话题名属于界面，所以走翻译；发给模型的 opener 仍是英文。

- `src/frontend/src/i18n/`：`zh.ts` 是**键名唯一来源**（`as const`），`en.ts` 类型是 `Record<MessageKey, string>` ⇒ **漏译一个键 = `tsc` 编译失败**，不靠跑起来才发现
- `index.ts` 用 zustand 存 `lang`，`detect()` 先读 `localStorage['lang']`，否则按 `navigator.language`；`format()` 只做 `{var}` 插值
- **刻意不引 react-i18next**：本项目 `.npmrc` 的存在就是因为这条网络连 registry.npmjs.org 都不稳，每加一个依赖都是未来一次装包失败（见「前端依赖两处钉版本」）
- ⚠️ **已知限制：localStorage 是 per-origin**。花生壳免费版的域名一旦轮换，语言偏好和登录态一样会丢 —— 这是偏好不是会话，接受此结果

**为什么有些地方是函数而不是常量**：`ScoreCard` 的 `STATUS_LABEL` 原本是模块级常量，常量在 import 时就固化成中文，切语言不会跟着变 ⇒ 改成 `statusLabel(status, t)`。**硬规则：面向用户的文案必须在取用时解析，禁止模块级中文字面量。**

同类问题还有 `useRecorder` 的 `MIC_HINTS`（一整张中文常量表）⇒ 改成 `MIC_HINT_KEYS` 键表 + **getter**，这样 8 个 `MIC_HINTS.denied` 调用点一行都不用动；配套的 `translate(key, vars)` 导出在 `i18n/index.ts`，供 React 渲染之外（模块 getter、事件回调、模块级函数）取词 —— 那里不能调 `useI18n()` hook。

> ⚠️ **已接受的交易**：解析发生在失败那一刻，所以学习者**在横幅还挂在屏上时**切换语言，那条旧文案会留到下次失败才更新。临时错误提示不为它把 key 贯穿到每个调用点；`AdminPage` 的 `feedback` 与 `ChatInput` 的录音提示则**存的是键+vars**（那两处会长期挂着或出现在手势中途）。

**接了 i18n 的界面**：`Layout`、`Home`、`BubbleSelector`、`Login`、`Register`、`History`、`ChatPage`、`ChatBubble`、`ScoreCard`、`ChatInput`、**`AdminPage`**；hook/工具层：`useRecorder`（`mic.*`）、`useSpeech`（`stt.*` + `tts.*` 共 6 条内联中文）、`useRecordingPlayer`（`replay.failed`）、`HistoryPage.messageOf`（`common.failed`）、`utils/format.ts` 的 `relativeTime`/`conversationLabel` 改为接收 `t`（原来直接把 `5m ago`、`Travel` 漏进中文界面）。

**边界（用户定的）**：后端返回的 `detail` 串、AI 回复内容、逐词反馈的 `expected_ipa` **不翻译** —— 多语言只覆盖界面显示。

**验证状态**：`npm run typecheck` / `npm run lint` / `npm run build` 均 **exit 0**（截至 2026-10-25 收完 hook 层那批）。⚠️ 真机上中英切换的实际观感**未验证**（无 vitest，也没有浏览器自动化），待用户在安卓/iOS 反馈。

#### 3.2.11 对话页语音优先（2026-10-25 新增，对应建议 5「削弱输入模式」）

用户选择：**折叠成「⌨️ 打字」切换**，不是彻底禁掉打字。

- 默认只显示大号 🎤 按住说话（`h-12 flex-1`），打字框与「发送」藏进切换后 ⇒ `localStorage['textMode']`
- ⚠️ **两种布局共用同一份按下/松开实现**（`micButton` 是一段 JSX，不是两份复制）：3.2.5 里那三层防卡死（`preventDefault` 抢手势、`finish()` 幂等、window/document 兜底监听）绝不能因为改了布局而降级

#### 3.4.1 对话回收站（软删除 + 7 天找回 + 强制删除）
- **删除 = 软删除**：`conversations.deleted_at` 置时间戳，不物理删除
- **列表/详情/发消息一律排除**已软删除的对话（恢复前对用户不可见，但数据完整保留）
- **找回**：回收站列出已删对话（含删除时间、剩余可恢复天数），一键恢复即清空 `deleted_at`
- **强制删除（永久删除）**：回收站内对**已在回收站的对话**立即物理删除，跳过 7 天等待
  - 路由 `DELETE /api/chat/conversations/{id}/purge`；**对活跃对话返回 400** —— 强制删除只能从回收站发起，避免一次误请求就把正在使用的对话连同录音一起毁掉（不可逆操作必须有"先进回收站"这道闸）
  - 与 7 天到期清理**共用同一实现**（`retention.purge_conversations`），不允许两处各写一遍删文件的逻辑，否则迟早一边漏删音频
  - 顺序仍是**先删文件、后删行**：反过来会丢掉 `file_path`，录音将永久滞留在磁盘上
  - 文件删除失败时**整体放弃并返回 500**，宁可留待下次重试，也不能出现"行没了、录音还在"的半删状态
  - 前端二次确认文案必须明说"无法恢复"
- **7 天后才真正清理**，且**必须一次做完三件事**：
  1. 删 `messages` / `audio_assets` / 关联评分行（3.2.5）
  2. **删磁盘上的音频文件** —— DB 级 `ON DELETE CASCADE` 只清行，**不会删文件**；不处理就会永久泄漏音频（还涉及隐私）
  3. 删 `conversations` 行本身
- 与既有 30 天音频保留策略（`AUDIO_RETENTION_DAYS`）**取更严格者**：对话被删后其音频随 7 天回收站一起走，不等 30 天

> ✅ **实现状态（2026-10-23 离线验证）**：以上各项均已落地。原 4 个查询（`list_conversations` / `_owned_conversation` / `messages` / `stream`）已全部加 `deleted_at` 过滤；`/conversations/trash` 声明在 `{conversation_id}` **之前**（FastAPI 按注册顺序匹配，否则 `trash` 会被 int 路径参数吞成 422）；定时清扫由 lifespan 每 6 小时调度（持 task 引用、关停时取消）。已验证：软删后列表隐藏且详情/发消息 404、越权删/恢复/强制删除一律 404、强制删除后**4 张表清零且磁盘录音同步消失**、活跃对话强制删除被 400 拦下且录音完好无损。

#### 3.4.2 自定义对话名（2026-10-23 新增）
对话此前只能按主题（`topic`，源自兴趣气泡）识别，多个 "Travel" 难以区分。

- **`conversations.title`**：用户自命名的名字，`String(60)`、可空；`PATCH /api/chat/conversations/{id}` 修改
- **显示优先级固定为 `title || topic || scene || 'Free conversation'`**，且**所有界面共用同一个回退函数** —— 否则改完名在列表生效、点进对话页标题却仍显示旧主题
- 校验：**先去首尾空白、再判长度**（`min_length` 若作用在原始串上，`"  "` 会通过校验、再被路由 strip 成空 → 一次空提交就能把名字洗掉，此坑已实测并修复）；上限 60 字符与列宽一致
- **改名入口有两处**（2026-10-23 补齐）：**历史页**每行的「改名」，以及**对话页标题栏**的「✏️ 改名」（就地输入，Enter 保存 / Esc 取消）。放在对话页是因为**只有在这里学习者才知道这段对话到底聊了什么**，回到历史页才想起来改名已经晚了
- 两处**共用同一个 store 动作** `useChatStore.rename(id, title)`：校验（trim 后非空、≤60）与请求只有一份实现。前端上限常量 `TITLE_MAX = 60` 也只在 store 里定义一处，与后端 `String(60)` / `ConversationRename.max_length` 对齐 —— 各页面各写一份 `60` 迟早漂
- ⚠️ **改名必须同时替换 `conversations` 里的那一条，不能只改 `current`**：`openConversation` 用 `conversations.find(...)` 重建 `current`，而 `send()` 每轮结束后都会重新打开对话 —— 只更新标题栏的话，**发下一条消息就会把名字静默打回旧值**
- ⚠️ **改名会 bump `updated_at`**（`onupdate=utcnow`），而历史列表按 `updated_at desc` 排序 → 该行会跳到列表首位。所以历史页保存后仍要 `refresh()` 重读（本地就地替换不足以保证顺序正确）；对话页不涉及排序，无需重读
- 历史对话不回填标题，按回退链自然显示；改名不影响既有评分/录音的外键关系

> ✅ **契约已入测试**（`src/backend/tests/test_conversation_rename.py`，8 项）：首尾空白被服务端 trim、`"   "` → 422、61 字符 → 422、改他人对话 → 404、匿名 → 401、列表读回新标题、`updated_at` 确实递增（断言用 `>` 而非 `>=`，空操作混不过去）、改名不误伤 `topic` / `deleted_at`。
> ⚠️ 未验证部分：**浏览器交互未实测**（输入框焦点、Enter/Esc、移动端窄屏下标题栏布局）。前端无 vitest，store 的"双写"只能靠上面的注释与后端契约测试间接锚定 —— 补上 vitest 后应把这条列为第一批用例。

## 四、非功能性需求

### 4.1 性能要求
- 页面加载时间：< 2 秒
- AI 响应延迟：< 3 秒（首字响应）—— 2026-10-16 实测基线：`qwen3.8-flash` 非流式**整段回复** 3.40s（326 tokens：prompt 183 / completion 143）；首字延迟需走 `/stream` 另测
- 语音识别延迟：< 1 秒（**未达标**：服务端 faster-whisper 实测 3.17s 音频 → 2.28s 推理，RTF 0.72，且是 4 核开发机所得；2 核 4G 会更慢。浏览器 Web Speech API 本地无此开销但拿不到音频、也无法做按住说话控制，见 3.1.5）
- 发音评测处理时间：< 3 秒（词级评测复用同一次转写，**不额外推理**；实测单条约 2.3s（4 核开发机），目标机待压测）

### 4.2 兼容性
- 浏览器：Chrome, Safari, Firefox, Edge（最新版 ± 2）
- 移动端：适配主流手机浏览器（响应式设计）

### 4.3 安全性
- 用户密码加密存储（bcrypt）
- API 密钥安全管理（环境变量）
- JWT Token 认证
- **学习者录音不得公开可读**（2026-10-23 定）：`/uploads` 静态挂载已删除，录音只经
  `GET /api/pronunciation/recordings/{asset_id}` 取回，**非本人一律 404**（与本项目"越权不暴露
  资源存在性"一致），文件已被保留策略清走则 410。
  ⚠️ **不要为了"让音频能播"再把该目录挂成静态文件** —— 录音与 TTS 同目录，一挂就等于公开人声；
  浏览器 `<audio src>` 带不了 JWT 头，正确做法是 axios `responseType: 'blob'` + `createObjectURL`（见 3.2.8）
- AI 合成音是**唯一**允许免鉴权头播放的音频，且必须走 `GET /api/speech/tts-file/{name}` 的
  `^tts-[0-9a-f]{32}\.mp3$` 严格校验（挡下 `user-*` 与路径穿越）—— 它是模型输出，不是学习者人声
- ⚠️ 尚未处理：`private/readme.md` 里的密钥已进 Git 历史（见第八节）；上传目录无 per-user 配额，
  磁盘占用只靠保留策略回收
